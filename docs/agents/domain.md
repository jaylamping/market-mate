# Domain context

[CONTEXT.md](../../CONTEXT.md) is the canonical glossary. Search for the terms relevant to the task, then read those sections; it contains future design as well as current concepts. Read the [architecture map](../architecture.md) to distinguish implemented capabilities.

Before changing a domain boundary, read the relevant [ADR](../adr/README.md) and its linked source/issue. Use the glossary's vocabulary. If a necessary concept is missing, propose its definition with the change rather than inventing a synonym across files.

Record durable decision rationale in an ADR; keep task status in GitHub or a task-specific handoff. ADRs retrospectively documenting shipped behavior must say so and must not invent a historical approval. Changes to Principal-owned authority or policy need the applicable explicit authorization.

If instructions, an ADR, and implementation disagree, describe the exact conflict and its consequence. Preserve authority/integrity boundaries while resolving it. Mark superseded ADRs with their replacements rather than deleting decision history.
